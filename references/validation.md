# 实际验码与结果说明

## 哪些工具负责识别

采用二维码解码器返回的真实内容进行比对。视觉模型可以评估材质和瑕疵，不能通过“看起来像二维码”来证明它可扫。

| 工具 | 调用方式 | 用途与边界 |
| --- | --- | --- |
| ZXing-C++ | Python `zxingcpp.read_barcodes(image)` | 默认配置作为常规基线；保留原始成功与失败 |
| Apple Vision | macOS `VNDetectBarcodesRequest`，限定 QR，读取 `payloadStringValue` | 本机独立识别路径；不是在真实 iPhone 相机里扫码 |
| jsQR | Node/JS，传入实际导出图的 RGBA 数组、宽高，记录反色检测选项 | 额外检查对图像结构、尺寸的兼容性；不能代表微信/小红书内部实现 |
| ZXing GlobalHistogram | 同一库的显式 `Binarizer.GlobalHistogram` 配置 | 诊断亮暗分布；必须与默认结果分列，不能算成另一套独立解码器 |

先检查环境是否已有库和运行时，复用可用依赖。缺少某个工具时报告未测试；不要把运行失败算成“未识别”，也不要把未执行项算成通过。Apple Vision 只在有该能力的 macOS 环境使用。

Apple Vision 可以通过当前环境兼容的 Objective-C 或 Swift 接口调用。根据本机 SDK 和工具链选择适配方式，不依赖其他机器的二进制或绝对路径。

## 三层检查

1. **原码基线：**解码原码，记录内容。获取原矩阵并检查排版使用的矩阵相同。若重编码是用户明确选择的新方案，记录它是重新编码后的码，不能声称仍是原矩阵。
2. **元素适配：**核对每件物件对应的暗格、浅格空隙、功能区域与静区。定位元素在完整测试码中验证。固定亮度阈值及格中心采样只用于发现风险；定位的异形角落或高光会使简单抽样与实际检测不同，不能用抽样结果单独宣布合规或失败。
3. **实际成品：**检测交付的完整海报文件，内容必须与基线匹配；记录各个识别器和配置的结果。标题、背景阴影、缩小、压缩和组合方式都可能改变整体检测结果。

视觉检查与上述测试同时保留：材质、微小轮廓、伪文字、透明边缘、拼接、定位与数据区的风格一致性、海报重心。扫码通过不免除视觉瑕疵检查。

## 测试条件

必测主要交付尺寸的实际 JPG，包括高清与实际使用的分享版本。明确宽高、JPEG 质量与编码设置，并从硬盘重读这些文件进行检测。先前 PNG 的结果不能代替新 JPG 的结果。

需要检查抗缩放/压缩能力时，可采用以下示例测试组作为起点：PNG 宽 2048、1024、768、640、512、384、256；768 宽 JPEG85；768 宽旋转 6°。保持比例、说明旋转填充色与插值方式，区分“实际交付文件”与“模拟变换”。不要为了凑九项而测试不会使用的尺寸，或把实际导出和模拟同尺寸计为同一文件。

按发布场景增加必要条件即可。例如视频截图、印刷与反光材质需针对相应文件或实物测试；电脑静态图不能模拟全部摄像头、应用、光线和观看距离。

## 简短记录

用 JSON 保存以下信息，字段名称可按工具适配，不绑定特定项目的脚本：

```json
{
  "source": {"file": "source.svg", "sha256": "...", "matrix_size": [25, 25]},
  "expected_payload": "从原码实际读出的内容",
  "quiet_zone_modules": 4,
  "tests": [
    {
      "file": "poster-share.jpg",
      "sha256": "...",
      "dimensions": [1024, 1536],
      "case": "实际分享 JPG",
      "encoders": {"format": "JPEG", "quality": 95},
      "decoders": [
        {"name": "ZXing-C++", "config": "default", "status": "pass", "payloads": ["实际解码内容"]},
        {"name": "Apple Vision", "status": "not_tested", "reason": "当前环境不可用"}
      ]
    }
  ],
  "physical_phone_test": "not_tested",
  "destination_check": "not_tested"
}
```

示例中的尺寸、质量和状态是结构说明，不能直接填成新任务结果。通过必须来自真实工具执行并核对内容；保存空结果、错误和不一致内容，不能只记录有利条目。注明工具版本和预处理，如有裁切、灰度化或改变阈值，作为单独条件记录。

## 完成状态

- 先按用户发布场景约定验收。没有更具体要求时，优先用默认 ZXing 和另一种可用的独立识别路径检查主要交付 JPG，额外记录 jsQR。工具缺项意味着范围有限，不能自行补成“全通过”。
- 如果某种配置通过而默认配置或其他要求的解码器失败，交代兼容性差异并继续针对原因修复。只在更宽松配置下通过的作品不能称为通用可扫。
- 对手机/app/印刷的保证，需要对应条件的真实实测。图片验码成功证明那些工具读出了内容；不证明当前链接落地页有效，也不证明物件符合条码标准认证。
- 局部修整后对实际新文件重新检测，不沿用旧版计数。小范围修改可以用窗口外差异与静区差异证明保留范围；不要同时声称艺术照片的所有格中心必然和原黑白码相同。
